# Design

## Context

动机见 `proposal.md`，行为合同见 `specs/storyboard-asset-binding/spec.md`。当前存在三个衔接断点：

1. `detail.assets` 来自 `workspace.assets`，`repository/project_workbench_read.go` 的 `ProjectUnitAssets` 只按已有 shot refs JOIN；零引用章节不能据此发现全项目候选。
2. `project-chapter-ai.ts` 把 `canvasAssets` / `characters` 放入 input，但 `provider.go` 的 `canvasGenerationInput` 不消费这些信息，不能认为模型已经看到资产。
3. `canvas-project-domain.ts` 输出合同含 `characters` 名称数组，`chapter-storyboard-production.ts` 却主要读取 `characterAssetId` 和 `assetBindings.nodeId`，名称结果不能稳定落成版本引用。

新镜头的 `replaceProjectUnitShots` 已接受 `assetVersionIds` 并在后端校验项目、最多 6 个引用和事务；不能把整章替换用于旧镜头补绑。既有 `UpsertShotAssetReferenceAndInvalidate` 即使同值引用也无条件 stale、取消 selected 并递增 project revision，因此不能循环调用它实现本次批量幂等。

本文件保留开案决策摘要，不是已实现证明；现有工作区变更归属和保留要求见 proposal。用户已确认的正式技术设计位于仓库 `docs/superpowers/specs/2026-10-22-storyboard-asset-auto-binding-design.md`，模块、接口、锁序和严格后置状态的实施细节以该文档为准。

## Goals / Non-Goals

**Goals:**
- 用独立候选加载、共享确定性解析和两种写入适配解决断点，限定在项目章节域。
- 让服务端成为权限、版本、容量、并发和失效的最终裁决者；前端仅承载预览与选择。
- 优先复用现有 revision 和引用表，以事务和集合差实现追加，不新增业务 schema。

**Non-Goals:**
- 不扩大工作区读模型、不改造通用画布协议、不新增别名字段或资产管理系统。
- 不为历史数据做自动回填，不通过模型推理匹配旧镜头，不引入后台付费任务。
- 不保留“引用已变但旧产物仍为当前有效选中”的假象；保留记录与保持有效状态不是同一要求。

## Decisions

### 1. 完整候选读取和提示词预算分离

按项目独立分页读取三类候选，复用既有资产/版本查询能力；不足的查询能力增加在项目 API，而非改造 `ProjectUnitAssets`。每次加载需要明确完成状态；任一页失败停止匹配并提示重试。候选包含现有资产 ID、类型、名称、有效版本标识及缺图状态；当前模型无 alias 字段，本版不做别名索引。无有效版本的资产仍用于解释“存在但不可绑定”。

完整候选用于匹配；模型摘要是另一份受限投影，只包含必要 ID、类型和名称，不发送媒体正文。第一版以序列化后 UTF-8 不超过 24 KiB 作为资产摘要硬上限，并服从上游总上下文限制；这个字节限额不是 token 容量保证。超额时仅按用户明确选择的资产范围或章节已有结构化引用缩减，并显示候选总数、发送数和缩减依据；仍超额或无明确缩减依据则阻止提交并要求缩小范围，不截取前 60 项或按任意排序截断。保守名称兜底的唯一性仍相对完整项目候选判断，不能因为提示词缩减隐藏同名冲突。

替代方案：将 workspace.assets 变全库会破坏读模型；仅扩大固定条数仍会静默漏项；均不采用。

### 2. 一个服务端解析核心，两种章节入口

在项目章节业务域内统一解析三类显式 ID / 名称线索，输出建议版本引用、依据及分类问题。新生成结果与旧镜头预览均调用该规则；前端不另写宽松版本的匹配器。名称仅做保守规范化（去除首尾空白），按类型唯一精确匹配，不猜别名、不消解歧义。旧脚本中的中文名称命中可用于未选中的提及候选，但不能把任意子串当作自动绑定证据；姓名台词不代表视觉在场。场景连续性只接受可追溯的结构化场景标识，无证据标记待确认；不传递上镜全部角色。

章节生成专用输入将摘要接入后端实际 prompt，专用输出显式提供项目资产 ID。结构化 ID 存在即先校验：非法、不属于项目或不在允许上下文内时报错，不能退回名称绕过；仅 ID 缺失时走唯一名称兜底。模型返回值和前端提交均是不可信输入，保存前重新检查所有权、版本可用性和容量。调整章节适配层而非破坏其他共享画布调用方。

替代方案：前后端各自匹配会产生规则漂移；让模型为旧镜头匹配增加成本及不可解释性；均不采用。

### 3. 新镜头沿用创建链路，旧镜头采用追加型批量能力

新生成先解析并展示无法自动解决的问题，容量合法的引用随新镜头走现有批量创建/替换链路落库；超限先选择，无图版本可绑定但不得假装存在参考图。图像和视频继续从持久化版本引用读取可用参考图。

旧镜头使用“预览”与“确认追加”两种操作；已确认路径及新生成解析接口见正式技术设计第 5 节。预览不写库，返回逐镜候选、理由、问题及并发快照。确认提交项目/章节、镜头 ID、选定版本集合及预览基线；返回各镜头实际新增数、无变化状态和刷新所需数据。服务端再次校验，不接受客户端自行声明权限或容量。失败使用统一 HTTP/业务错误合同及机器可读 reason；整个批次成功或失败，不返回隐式部分成功。

替代方案：整章替换可能破坏镜头 ID、脚本和产物；逐镜请求无法保证原子性；均不采用。

### 4. 并发基线采用现有 revision 加完整快照，事务内原子裁决

预览基线至少包含：项目 revision、章节与镜头归属、脚本 revision、每镜排序去重后的完整引用集合（保留行身份、role/status）、建议版本所属资产及其有效状态指纹，以及产物内容和状态快照。版本指纹覆盖决定引用和参考图含义的当前版本关系、可用/删除状态和媒体引用，不能只比较版本 ID。哈希必须来自规范化序列化，不依赖列表显示顺序。基线由服务器产生，客户端回传仅作非信任乐观锁条件，不是授权或预览防伪凭据；本版不引入未经核验来源的签名密钥。前端持有快照不替代服务端重新读取和鉴权。

确认事务先取得相关资产拥有者域协调锁，再按固定顺序锁定项目、镜头和资产/版本等对象，读取完整基线后计算集合差、容量并原子写入。PostgreSQL 使用 namespace 为 storyboard-assets:userID 的 advisory_xact_lock；SQLite 在事务读取前对 assets 表执行无匹配行 UPDATE 取得写权限，仿 upload_reservations.go 的机制但不使用 upload 表。跨所有者稳定排序，管理员取对象所有者，共享资产覆盖所有关联项目；鉴权不等于锁所有者。仅直接竞争的脚本/引用、替换删除、关联解除、版本/媒体写及资源删除入口加入同协议，协调锁必须先于这些入口的行锁。project revision 仅作辅助，修复旧绝对值回写并采用事务内递增/CAS；不全局事务串行化、不在持锁段调用远程服务。保留既有资源删除与 Outbox 边界，不虚构统一 deleting 状态，不将数据库保护等同外部对象可用。上线前以双数据库关联/删除竞态测试验证，不能凭方案宣称已具备原子保护。

原基线一致时正常应用；相同确认的重试只允许一个严格无写入分支：全部目标镜头脚本与版本指纹仍一致，引用集合精确等于“原集合 ∪ 本次选定集合”，没有额外增删或 role/status 改动，产物符合一次失效后的精确状态且无后续编辑，项目 revision 为预期成功后 revision（实增批次只递增一次）。此时返回无变化；任何其他变化都要求刷新。不借“已包含选定引用”跳过权限或其他并发检查。无新增的初次确认保持原 revision。该方案是状态幂等，不需要新增持久幂等表，也不声称能证明请求曾经执行的历史。

替代方案：只比较时间戳无法覆盖所有写路径；只比较选定 ID 会漏掉其他引用改动；新增持久幂等表超出本次最小范围。项目级 CAS 较保守，可能因无关项目更新要求刷新，优先选择安全而非细粒度并发。

### 5. 失效只发生在真实集合增量之后

先计算每镜新增集合，空集合不写引用、不失效、不递增 revision。非空集合在同一事务中复用既有失效语义，相关产物 stale 且 selected=false，保留全部历史产物记录和内容。需要将失效规则与“无条件 upsert 后失效”的调用方式区分，不能循环调用当前 `UpsertShotAssetReferenceAndInvalidate`；可提取事务内失效逻辑供实增分支复用，但不顺手重构无关调用方。

替代方案：无条件调用旧 helper 破坏幂等，保留 selected 则会把已过期产物表现为当前结果，均不采用。

### 6. 预览遵循既有产品容器和设计 token

使用现有 `AppModal` / `AppDrawer` 与 tokens，按镜头展示已有引用、建议版本、依据、缺图、无版本、歧义和容量；默认只选明确有效且容量合法的结果。超限组不得任意预选前若干项，由用户选择。确认前说明实增会使相关产物过期并取消选中，但不会删除产物；取消只关闭预览。冲突后禁用旧快照确认并重新获取预览。前端 API 走既有 `http` 调用面，取消请求保留取消语义。

替代方案：独立 HTML、全局样式补丁或确认前先保存都会绕过现有页面状态和交互约束，不采用。

## Risks / Trade-offs

- [规则保守导致漏匹配] → 明示未匹配/待确认并允许人工选择，不以猜测换覆盖率。
- [分页期间资产发生变化] → 加载完整状态与预览快照分离，最终在事务中重新校验；无法取得一致候选快照时刷新，不承诺静态全集。
- [旧写路径未推进 revision 或未遵守锁协议] → 将写路径核对、CAS 冲突及跨数据库并发测试作为上线条件；不能凭方案文本宣称已解决。
- [字节预算不等于模型 token 预算] → 同时保留上游上下文限制和明确缩减提示，不宣称完整上下文；预算值集中维护，可依据真实协议测试调整。
- [已有 diff 与本变更重叠] → 只修改必要片段，保留 `projects.ts`、OpenAPI、docs 等已有差异，不清理、不归因、不提交既存改动。

## Migration Plan

无需自动数据回填；旧章节仅在用户预览确认后补绑。先上线候选读取、解析与追加事务能力，再接入章节生成和预览 UI，同步 API/OpenAPI、功能概览、代码地图与 pending-test。若实施确需新增 schema，须先修订本设计并同步数据库文档，不能以当前“无 schema”假设掩盖迁移。

回退时关闭或撤下新增入口，不删除已写入的合法引用和历史产物，不恢复 stale 产物为有效选中；不得通过整章替换回滚补绑结果。当前阶段仅规范检查，不执行上述上线、数据变更或业务测试。
