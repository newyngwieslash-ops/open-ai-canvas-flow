# 源铭振跃产品品牌技术设计

本设计细化用户已确认的实现方案。范围与验收合同以 `docs/openspec/changes/rename-product-brand-to-yuanming-zhenyue/specs/product-brand-identity/spec.md` 为准；本文件不建立第二份需求规范。

## 现状与改动边界

此前欢迎页已经改用新品牌及暖色奇幻场景。前端 `brand-display.ts` 仍只是显示映射，后端外观、认证和 Agent 默认名没有更新。只读检查当前 `/api/public/appearance`，品牌、SEO 标题/描述、版权和 Agent 名均返回旧身份。

品牌来源分散在前端降级配置、后端 appearance、auth 默认值、自有提示词与技能、插件清单及实际归档。初步审计得到 377 个文本文件、592 个命中行，105 个插件包中有 94 个包内存在旧中文品牌。这是检查基线，不代表所有命中都应替换，也不代表图片和视频已验证。

现有欢迎页及其测试和素材作为已获授权的输入保留。用户上传参考图、`.taste-skill/`、项目创作数据与无关工作区改动不纳入批量修改。

## 实现策略与数据流

采用用户确认的方案：修改真实默认值与既有规范化入口，复用官方内容同步机制，逐项更新分发素材。只扩展前端映射不能覆盖邮件和包内输出；全库字符串替换会误改用户内容与技术合同，均不采用。

```text
保存的外观 JSON / 新默认值
  → readAppearance 的字段规范化
  → 公开外观、管理外观、站点身份
  → UI 元数据、默认协议、继承式邮件身份

自有技能 / 插件源码
  → 既有加载与打包路径
  → 按稳定 ID 更新官方条目
  → 用户看到的新名称、作者与说明
```

### 默认值与存量外观

修改 `web/src/stores/use-appearance-store.ts`、`backend/internal/app/appearance.go`、`backend/internal/auth/host.go` 和前后端 Agent 默认值；可见英文旧品牌改为新中文品牌或中性功能说明。沿已有 appearance 消费路径统一输出，收敛仅用于 UI 的重复品牌映射，不增加页面级补丁或通用品牌服务。

存量处理集中在读取和合法保存共用的规范化边界。GET 继续只读，不隐式写数据库。规范化必须幂等，公开和管理投影一致；后续保存包含新值，未保存时重启也能从旧值稳定得到新输出。

| 字段 | 处理规则 | 保护边界 |
| --- | --- | --- |
| brandName | 去空白后精确等于旧默认名时更新；空值沿现有默认回退 | 其他自定义名称保留 |
| SEO 标题、说明、版权 | 仅替换已确认的旧默认值及其明确派生模板；年份等非品牌部分保持 | 自由文案不进行无条件 replace |
| canvas.agentName | 精确旧默认名更新；空对象沿既有默认路径 | 自定义助手名称保留 |
| Agent 其他展示文案 | 更新产品内置模板，保持占位符合同 | 自定义文本、系统提示词和权限不批量改写 |
| 媒体、主题、备案、购买入口、公告 | 不因改名修改 | 完整保存前后逐字段比对 |

保留旧默认识别字面量作为必要迁移输入，并在审计中注明位置与用途。异常 JSON、鉴权和校验仍走既有错误路径，不以默认配置掩盖数据错误。若当前运行实例需要显式保存，先备份完整原设置，通过现有受保护更新接口写入；不得点击恢复默认、直接改库或打印密钥。

### 邮件、协议与助手

`resolveEmailSender` 与 `publicEmailSetting` 对继承式发件人的判断保持一致：空名、旧默认名和新默认名按既有约定继承当前站点品牌；其他发件人名不变。所有调用方共用这一个判断，避免邮件实际发件名与管理页的继承标记不一致。

默认注册协议继续由站点品牌派生；自定义协议不无条件覆盖。更新前端创作/剪辑助手、后端自有媒体策略、预演字标、作者回退及恢复默认提示的真实源头。验证码与重置邮件回归使用隔离发送器，不发送真实邮件；不通过真实注册或恢复默认操作验收。

### 内置技能与插件分发

短剧技能中文目录、名称和作者同步更名并修正引用，保留 `yingce-short-drama-workflow` 等稳定 ID。既有 `EnsureBuiltinSkills` 按 ID upsert 并维护内容版本，用户加入和收藏关系在独立状态表；沿用该机制，不新增迁移框架，不扩大官方种子覆盖范围，不强制升级用户固定的安装版本。

插件启动流程已检查官方源包、刷新包缓存与注册表，并保留启用状态。更新源 manifest、内嵌 documentation、README 和实际 `.yingce-plugin` 包，复用现有打包能力；不足的机械归档步骤使用标准库实现，不引入依赖。品牌元数据不应顺带改变协议、能力参数或供应商地址。

解包核验全部 105 个分发包，比较每个受影响包的源码和包内展示文本，并检查稳定 ID、资源引用和协议参数。验证已有官方条目刷新、禁用状态保留、自定义条目隔离及宿主导入行为；不能只依据包外源码或二进制 grep 判定完成。

### 视觉素材、文档与残留审计

按引用核查图片、截图、SVG、HTML 和视频。`logo.svg` 为中性图形，无须重画。原欢迎页截图仍有旧品牌像素，虽然当前欢迎页改用新截图，仍需记录其他引用并处理。产品截图从改名后的真实路由重截，不能用生成界面冒充验收。外部媒体逐项记录实际可检查范围，无法访问时明确标为未验证。

更新自有品牌文档、维护说明、注释、脚本显示与 OpenAPI 标题。保留真实第三方作者、许可证、上游链接和镜像来源。普通词语如“摄影策略”不属于品牌；历史研究文件和用户参考输入不自动视为当前产品文案。

留下一个聚焦的可运行扫描，覆盖文本、文件名及归档条目，并为扫描自身保留最小回归。例外精确到文件和用途，分类为迁移识别、回归输入、稳定机器标识、真实出处及历史/用户参考；不使用宽泛目录白名单掩盖产品残留。图片和视频检查表独立记录，扫描通过不代表视觉通过。

## 技术合同与错误处理

保留 API 路径、JSON 结构、Cookie、缓存/存储键、`YINGCE_AGENT_*`、Go module/import、部署服务名、实际镜像及仓库地址、插件协议/扩展名/稳定 ID。无需 schema 变更、清库、重装或数据兼容层。

源包无效、设置格式错误和保存失败继续向上报告；不吞错、不回写默认配置。归档验证失败不得将旧包视为已完成。回滚仅针对本次补丁和本次有备份的设置写入，不回退此前 UI 成果或删除用户数据。本次不推送、不部署。

## 验证策略

1. 在现有测试中补最小回归：旧默认外观、自定义品牌/Agent、完整字段保留、规范化幂等、读取/保存/重读、邮件继承与默认协议；不为纯文案替换逐条写实现镜像测试。
2. 检查前端初始、成功加载和失败降级品牌一致，页签标题和版权不闪回旧名；运行相关前端专项、类型检查、项目 lint/build，以及后端外观、认证、技能和协议相关包。
3. 核对内置内容稳定 ID、用户关系和插件启用状态；逐包解压并用现有导入测试验证分发产物。
4. 使用已运行的真实应用检查登录、注册、找回密码、创作/侧栏、后台外观、预演、助手、欢迎页，检查明暗主题、关键焦点与必要的 320/375/414/768/1440 宽度。受限路由如实记录，不将静态阅读写成运行通过。
5. 最终重扫并逐项复核素材和例外，将命令、截图、包内核验及未覆盖边界写入交付记录；同步 features、pending-test 和受影响专题。
